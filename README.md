[![CodeQL](https://github.com/philfanzhou/Emenda/actions/workflows/codeql.yml/badge.svg)](https://github.com/philfanzhou/Emenda/actions/workflows/codeql.yml)
[![Release](https://github.com/philfanzhou/Emenda/actions/workflows/release.yml/badge.svg)](https://github.com/philfanzhou/Emenda/actions/workflows/release.yml)

Self-hosted, AI-driven mistake management service for learning platforms.

Emenda owns the mistake lifecycle: intake, AI-assisted image analysis, review, practice
tracking and process history. It is extracted from the [Ruoyu.Study](https://gitee.com/philfanzhou/Ruoyu.Study)
platform, where it ran as the Mistake service; the git history of that service is preserved
in this repository.

## Status

Emenda is configured from standard appsettings/environment configuration, owns a dedicated
PostgreSQL database and S3 bucket, and authenticates trusted backend callers with a
per-caller credential.

Mistakes enter through two paths, both backed by the paired AI Tutor service:

- **Automatic extraction** (`POST /api/intake/extractions`): StructaDoc layout plus AI Tutor
  multi-image recognition and judgement; only incorrect attempts become pending-review mistakes.
- **Conversation collection** (`/api/mistakes/conversation-collections`): mistakes collected
  from AI Tutor conversations.

## Configuration

Configuration comes from `appsettings*.json` and environment variables. Start the container
with `./start.sh` (or the same environment variables):

| Environment variable | Required | Purpose |
|---|---|---|
| `EMENDA_DB_CONNECTION` | yes | PostgreSQL connection string of a dedicated Emenda database (`ConnectionStrings__Emenda`) |
| `EMENDA_API_KEY` | yes | Per-caller credential value (`Emenda__Security__Callers__0__ApiKey`) |
| `EMENDA_CALLER_NAME` | no | Stable caller name for audit and the intake idempotency namespace (default `platform`) |
| `OSS_INTERNAL_ENDPOINT` / `OSS_ACCESS_KEY` / `OSS_SECRET_KEY` / `OSS_BUCKET_NAME` / `OSS_PUBLIC_BASE_URL` | yes | S3-compatible object storage (`Oss__*`) |
| `EMENDA_ADMIN_AUTHORITY` / `EMENDA_ADMIN_CLIENT_ID` / `EMENDA_ADMIN_CLIENT_SECRET` / `EMENDA_ADMIN_REDIRECT_URI` / `EMENDA_ADMIN_POST_LOGOUT_REDIRECT_URI` | no | SignaCore hosted login for the admin console (`Emenda__Admin__Oidc__*`) |

The optional **admin console** at `GET /admin` uses SignaCore administrator login and
manages dynamic credentials. Before a **new installation**, explicitly initialize the
persistent caller file with `./start.sh --init-callers` using the same image/data mount as
the service, then run `./start.sh`. Initialization never overwrites an existing file.
Missing or invalid configured credential state fails closed with HTTP 503; restore lost
state rather than bootstrapping over historical revocations. Console writes are immediate;
direct file edits require a restart. See [Admin Console](docs/development/AdminConsole.md).

Business requests under `/api/*` must carry `X-Emenda-Api-Key`. Health (`/health/live`,
`/health/ready`), the contract endpoint (`/contracts/*`) and the root endpoint stay
anonymous. Callers own student authorization; API keys identify trusted backends, not
isolated tenants. Review rejection changes local state and preserves images. See
[Deployment](docs/development/Deployment.md).

### Automatic extraction

The asynchronous intake at `POST /api/intake/extractions` preserves originals, uses
StructaDoc layout plus a paired AI Tutor multi-image analysis API, and creates
pending-review items only for source-backed incorrect attempts. It supports one image
with multiple questions and one question spanning multiple images. Correct and unknown
results remain available without creating mistakes.

The desktop SignaCore workspace **错题入库** at `/admin/extractions` lists client-submitted jobs and provides original-image region
editing, grouping and judgment correction, version history and explicit failed-job retry.
The feature defaults off; see [Automatic extraction](docs/modules/AutomaticExtraction.md)
and the [paired AI Tutor implementation](integrations/ai-tutor/README.md) before enabling it.

### HTTP contracts

The lifecycle contract is [mistake-http-v6](docs/Integration/mistake-http-v6.json) and the
extraction contract is [emenda-extraction-v2](docs/Integration/emenda-extraction-v2.json);
both are served anonymously under `GET /contracts/{version}.json`. Earlier published
documents (`mistake-http-v1`…`v5`, `emenda-intake-v1`, `emenda-extraction-v1`) stay available as historical versions.

### Display sizes (schema v23)

Every displayed mistake image (legacy, extraction original/supplement/crop and conversation evidence)
has `medium` (800 px), `small` (400 px) and `thumbnail` (200 px) JPEG variants next to it. They are
queued when an image is written, generated by a background worker, rendered on demand when missing and
removed together with their parent, including when an administrator deletes a task; retained confirmed
mistakes keep their crops and thumbnails. Schema v23 queues all existing images, so current tasks and
confirmed mistakes are backfilled automatically. See [Display sizes](docs/Integration/ImageVariants.md).

### Database schema v20

Schema v20 adds persistent AI proposals, original-question supplements and crop cleanup.
Only current incorrect items have formal crops; originals and accepted supplements stay.
Old geometry, checkpoints and log crop snapshots are retired irreversibly while version
and idempotency receipts remain. Object references are fenced against physical cleanup.
Read [v2 corrections](docs/Integration/extraction-corrections-v2.md) before deployment:
the existing-data geometry migration requires a reviewed inventory and authorization,
even when `CleanupLegacyObjects` is false. Shared test/production acceptance is separate
from a successful build.

### Database schema v19

Schema v19 drops the managed source tables (`source_*`, `legacy_return*`, `layout_job*`)
and their guard triggers. The upgrade locks those tables and refuses to run, leaving the
database unchanged, if any of them holds a row; mistakes, practices, logs, extraction,
conversation and analysis data are untouched. v19 is forward-only. See
[migration history](docs/database/migrations.md).


## Layout

- `src/` — service solution (`Host`, `Service`, `Domain`, `Database`, `Tests`)
- `docs/` — versioned HTTP contract and documentation
- `manifest/` — minimal source package manifest used by the build rehearsal
- `vendor/` — shared components vendored from Ruoyu.Study and maintained independently here
- `start.sh` — container start entry point

## Build

```bash
dotnet build src/Emenda.sln -c Release
dotnet test src/Tests/Emenda.Domain.Tests/Emenda.Domain.Tests.csproj -c Release
```

The database-backed suites need PostgreSQL 15 and a dedicated connection; the image build
needs Docker.

For real PostgreSQL + S3 acceptance, use the repository-owned
[standalone verification entry point](docs/development/StandaloneVerification.md).

## Container images

`release.yml` publishes multi-platform (amd64/arm64) images to GitHub Container Registry
for version tags only; merges to `main` run CI and do not build images.

| Tag | Meaning |
|---|---|
| `ghcr.io/philfanzhou/emenda:latest` | latest stable release |
| `ghcr.io/philfanzhou/emenda:X.Y.Z` (also `X.Y`, `X`) | stable semantic version |
| `ghcr.io/philfanzhou/emenda:X.Y.Z-rc.N` | prerelease |

Every tag also produces a GitHub Release with generated notes. See
[Automation](docs/development/Automation.md) for the workflow contract and the release
process.
